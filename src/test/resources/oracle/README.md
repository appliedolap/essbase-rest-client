# Grid operation oracle

What Essbase actually does for the ad hoc grid operations, captured from a live server so that a
client-side implementation of them can be diffed against the engine rather than against someone's
recollection of the engine.

The reason this exists: the Planning REST API has no ad hoc verbs at all, only "retrieve". Jaygrid
implements zoom in, zoom out, keep only, remove only and pivot locally and submits the rewritten sheet
as a plain retrieve. Whether it matches Essbase is an empirical question, and these files are the
answer key.

Written by `KeepRemoveOracleIT` against `Vision.Plan1` - the Planning application imported into Essbase
from an EPM Cloud artifact snapshot, so the same outline is available in both places. Re-run it with:

```bash
mvn -Pintegration-destructive verify -DallowDestructiveEssbaseTests=true -Dit.test=KeepRemoveOracleIT -DfailIfNoSpecifiedTests=false
```

## What a fixture holds

| field | why it is there |
| --- | --- |
| `basis` | the grid the operation was applied to - **as the server answered with**, not as it was asked for |
| `operation` | the action, the `[startRow, startColumn, rowCount, columnCount]` ranges, and the labels those land on |
| `result` | the grid that came back |
| `aliasTable` | the labels are aliases, so `ALL` goes in and `All Accounts` comes back |
| `preferences` | `includeSelection`, `withinSelectedGroup`, `zoomInPreference`, the suppressions - these decide much of the answer on their own |
| `headerRows` / `leftColumns` | the two numbers that divide a grid's three regions |

A grid has three regions, and every dimension is in exactly one of them - POV plus top/column axes plus
left/row axes always sums to the cube's dimension count. `placements` records which, taken from the
server's own report rather than inferred from the labels: a layout the server quietly reinterpreted
looks perfectly reasonable in the labels and is only visible there.

## Rules the corpus establishes

**Keep only and remove only constrain a column, not a row.** Selecting one member in one left column
filters that column's dimension to the members picked in it and leaves the other left columns alone.
So keeping `All Accounts` at a single cell keeps it under *every* entity, not the one tuple clicked.

**Two selections in two different left columns intersect, they do not union.** Keeping
`Management Rollup` in the entity column and `Cash Flow` in the account column leaves the one row that
is both - not the two rows the two cells were on. This is the one most likely to be implemented wrong,
because the selection arrives as a list of cells and keeping the rows those cells sit on is the obvious
reading.

**A selection on a data cell does nothing.** The grid comes back untouched - not the row, not the
column, not their intersection. Caveat: this cube holds no data, so the cell is both a data position
and empty, and nothing here separates "ignores data cells" from "ignores empty cells".

**Selections on the top axis behave the same way**, one grid row instead of one grid column.

## What is not here yet

Pivot, zoom in and zoom out. `GridOracle.Action` already covers the zooms; they need a corpus written
with the zoom preferences varied, because `zoomInPreference`, `includeSelection` and
`withinSelectedGroup` change those answers far more than they change these.

## What the diff found, and what was changed

`EssbaseOracleDiffTest` replays every fixture through `CubeViewImpl` against `vision-plan1.yaml` - the
outline the corpus was captured from, generated by `OutlineYaml` in essbase-rest-client - and compares
the left axis, the top axis, and where blank rows ended up. It is an ordinary offline unit test; the
live server was needed to write the corpus, not to run it.

The first run diverged on every case with two dimensions on an axis, and on selections involving data
cells and blanks. Three changes brought them into line.

### A selection constrains an axis position, not a grid row

`AbstractRangedOperation.perform` used to call `performOnLeft(grid, rows(ranges, offset))`, where
`rows()` read only each range's start row and row count - the **column** of every selection was
discarded, so the operation kept or removed whole grid rows. Essbase instead constrains the selected
column's own dimension and leaves other columns alone, so it now reads each selected cell as a member
picked in one axis position:

- two members picked in one position are a **union**
- positions are combined by the operation: keep only **intersects** them, remove only **unions** them
- a position with nothing picked in it constrains nothing
- the top axis is identical, rotated - its positions are rows where the left axis's are columns

With a single dimension on an axis all of this collapses into "keep the rows that were clicked", which
is why the existing tests passed either way. `CubeViewKeepOnlyTest.keepOnlyOnLeftWithoutPov` and its
Remove Only counterpart were reworked: both clicked column 0, which held `West`, while asserting on
`Feb`/`Jan` - the intent was the inner column, so they now select it, and new tests cover the outer
column, the union and the intersection.

Confirmed alongside: Essbase refuses a Remove Only that would empty the axis ("You must have a row
header in order to perform this retrieval"), which is what Jaygrid already did.

### Region boundaries were inclusive where they are counts

`IntermediateGrid.region(int, int)` answered `LEFT` for `column <= leftColumns()`, and `leftColumns()`
is a count - so the first data column sat inside the left axis, and a click on the top-left data cell
kept that row. Its `DATA` branch needed `row > topRows() + pov.getRows()`, excluding the first data
row, so a cell further right in that row came back `NONE`. Both are now exclusive-bound comparisons.
Essbase ignores a data-cell selection; so does this. No existing test depended on the old behaviour.

### Zoom and pivot ignored a selection that names no member

The ranged operations skip a cell that names no member. Zoom and pivot reach the grid by a different
path - `AbstractSingleRegionSourceOperation`, a single source cell rather than a list of ranges - and
had no such guard: zoom ran off the end of the axis and pivot acted as though the adjacent real column
had been clicked. Confirmed against the engine first (`ZoomOracleIT`): Essbase does nothing for zoom in
or zoom out on a blank row, zoom in on a blank column, or zoom in on a data cell. Now neither does this.

### A multi-cell selection kept only its last cell

`addCell` on a single-source operation overwrote rather than accumulated, so zooming a selection of
several cells zoomed only the last one and dropped the rest in silence - and the connector's Zoom In
adds one cell per selection Dodeca reports. Essbase expands every selected member in place, verified in
`ZoomOracleIT`, so now so does this.

Two details the corpus settled rather than guessed. The cells are acted on from the far end of the axis
back, because each operation rewrites the axis it acts on and only disturbs positions after the one it
touches. And each is checked still to be where it was read before being acted on, because zooming out
one member of a group collapses the whole group - the second cell picked inside it then has nothing
left to act on, which Essbase shows by collapsing four entities to one row for a two-cell zoom out. The
check is of the position rather than a search for the member, since with repeated member labels a
search answers with the column's first row whichever row was picked.

### Blank rows and columns were not counted when resolving a selection

An axis grid holds only its real tuples - a blank is taken out at interpretation and remembered
separately - but `localRegion` subtracted only the header offset. So every grid position past a blank
named the tuple one place too early, and the last one ran off the end of the axis. `localRegion` now
maps a position through the blanks, and answers "no member" for a blank itself, which makes a selection
on a blank do nothing, as it does in Essbase. A selection that names no member at all is now a no-op
rather than a Keep Only that keeps nothing.

## The ad hoc options

Zoom's answer depends on the preferences far more than keep only's does, so the corpus varies them one
at a time against a single baseline - Essbase's own defaults, written out in `GridOracle.DEFAULTS`
rather than read, because the preferences resource is per session and not per grid: a capture that did
not state them would inherit whatever ran before it.

What the engine does, with everything else held at the baseline:

| option | effect |
| --- | --- |
| `zoomInPreference` | `NEXT_LEVEL` gives the children; `ALL_LEVELS` every descendant level, intermediate levels included; `BOTTOM_LEVEL` the leaves only |
| `includeSelection` | off, the expanded member is replaced by its children rather than kept after them |
| `removeUnselectedGroup` | on, every row outside the selection goes |
| `withinSelectedGroup` | on, an **inner** member expands only under the group it was picked in. No effect at all on an **outer** member |
| `repeatMemberLabels` | off, a repeated outer label is left blank under the one above - a continuation cell, not a blank row |

The replay applies each fixture's recorded preferences before running it. Without that the comparison
is not of the same question: `includeSelection` alone is the difference between a zoom that leaves the
expanded member on the grid and one that replaces it, and it was the first thing the zoom fixtures
disagreed about. Enum values are matched by name with the underscores removed, because Essbase's
`SUBITEMS` is Jaygrid's `SUB_ITEMS`.

### `withinSelectedGroup` narrowed the wrong thing

The option decides *where* a member is expanded, not *how much of a run* is replaced - and the two had
been conflated. `performOnGeneric` used to answer bounds of `{row, row + 1}` whenever the option was on,
replacing a single row, and to use the run containing the selection whenever it was off.

Both halves were wrong, and in opposite directions. An outer member spans a group of rows - `Total
Entity` covers both of its account rows - so replacing one of them lost the account pairing from the
expanded rows. An inner member appears in several runs of the axis that do not touch, one under each
outer member, so using only the run the selection sat in expanded it under that outer member alone -
which is what the option being *on* is supposed to mean, leaving both settings answering the same thing.

It now reads as Essbase does: `GridExpansionRangeFinder.findAll` gives every run of the member down the
column and all of them expand, unless the option is on, in which case only the run the selection sits in
does. A member spanning a group replaces that whole group either way. The runs are expanded from the
bottom up, because an expansion changes how many rows lie below it.

### `removeUnselectedGroup` had no equivalent at all

Essbase carries it on `/preferences/grid` as `removeUnSelectedGroup`, and `CubeViewOptions` had nothing
to match it, so a zoom always behaved as though it were off. It is now an option of the same name,
defaulting to off so that nothing which does not ask for it changes.

What the engine does with it, from six fixtures rather than one - a single dimension on the left leaves
too much unsaid:

- what survives is the members that were picked and what they expanded into; the rest of the axis goes
- the judgement is made in the column that was zoomed. Zooming an account removes the unselected
  accounts from under every entity and leaves the entities alone; zooming an entity removes the
  unselected entities and leaves the accounts alone
- `withinSelectedGroup` scopes it: with both on, only the group the selection sits in is expanded or
  pruned, and the rows outside it are left exactly as they were
- with more than one cell picked, "unselected" means none of them
- it says nothing about a zoom out

It runs once, after every selected cell has been expanded, rather than per cell - "unselected" is a
statement about the whole selection, and doing it a cell at a time would take the second cell's rows
away before the second cell had been reached.

## Known divergence: repeated member labels

`zoom-in-without-repeating-member-labels` is the comparison asking the wrong question rather than a
difference in the zoom, which now agrees. An intermediate grid names the member on every tuple of an
axis; whether a repeated label is written or left blank under the one above is decided when the grid is
written back out. So the blanks Essbase answers with cannot line up with an axis comparison whatever
Jaygrid does. Checking it properly means comparing the rendered grid.

## Known divergence: where a blank row lands

Essbase keeps a blank row that any surviving row follows, and places it immediately before the first
such row; a blank nothing survives after is dropped. Jaygrid remembers the blank's position and
re-inserts it there, which after rows are removed lands it after the row it used to precede, and keeps
it when it trails. The members agree in both cases - only the spacer moves.

This is recorded rather than fixed, because it needs the blank positions recomputed where rows are
removed rather than a change at the point of selection. `keepOnlyBelowABlankRowPlacesTheBlankDifferently`
and `keepOnlyAboveABlankRowKeepsATrailingBlankEssbaseDrops` assert Jaygrid's current placement and will
fail if either side changes.

## The connector-shape characterization

`ConnectorShapesCharacterizationTest` is the other half of this and lives beside it. Where the corpus
here says what is *correct*, that one pins what Jaygrid *currently does* across all five operations over
the grid shapes the Dodeca PBCS connector actually sends - a seven-deep top axis with no POV, the same
with a blank column, a wide horizontal POV, two dimensions on the left. It exists because the
connector's own coverage of these operations is entirely in live-EPM integration tests that an ordinary
build never runs, so without it a change to a shared rule moves connector behaviour silently.

Regenerate it with `GenerateCharacterization` only after reading the diff and agreeing it was intended.

## Pivot: the REST action is a general move, addressed by flat cell index

Both pivot actions take **flat cell indices** - `row * columns + column`, counted across the grid row by
row. Not row/column pairs, not column numbers. Oracle's documented `pivotToPOV` example sends `[8, 2]`
for a four-column grid, which only makes sense read flat, and `PivotOracleIT` asserts the behaviour that
follows from it against a live server.

Read that way the action is the general "move this dimension there":

| call | effect |
| --- | --- |
| `pivot [cell]` | that dimension to the front of the row axis, from the POV or from the column axis |
| `pivot [from, to]` | that dimension to wherever the destination cell is - POV, row axis or column axis |
| `pivotToPov [from, to]` | that dimension into the POV, backfilling the axis it leaves from the POV |

It refuses what it should: taking the last dimension off an axis is "Cannot pivot last row", and naming a
data cell is "Pivot starting point cannot be determined".

**An earlier pass of this corpus concluded the opposite** - that the source had to be a POV dimension,
that `pivotToPOV` was refused from every cell of a grid, and that a row dimension could only be made a
column dimension through `setLayout`. Every one of those came from probing with column indices and
row/column pairs, which the server rejects or misreads without saying why. The measurements were real
and the coordinate space was assumed. Worth remembering as the shape of the mistake: a black-box sweep
that never checked its encoding against the vendor's own example.

`setLayout` is still the way to describe a whole layout at once, and still the only mechanism a client
computing operations locally has. It is not, as this file previously said, the only way to rearrange a
grid.

## Pivot: the REST action cannot express one

The pivot action works, and reliably - within a domain much narrower than its name. It moves a dimension
**out of the POV onto an axis**, and does nothing else.

Its two coordinates are **grid columns**. The source names a column of the POV row, and every POV
dimension can be moved: to a column inside the left axis it becomes a left dimension at that position,
to the first data column it becomes the outermost top dimension, and to anything further right the call
is accepted and does nothing. Given a settled grid the answer is the same every time.

What it will not do is take a dimension that is already on an axis. Naming a left column as the source
is refused whatever the destination, on grids the server built itself as well as on constructed ones -
so a row dimension cannot be made a column dimension, and an axis cannot be reordered. `pivotToPov` does
not fill the gap either: it is refused from every one of the thirty cells of a two-by-two-by-four grid.

**Two traps make this look far worse than it is**, and both caught an earlier pass of this work. The
stored ad hoc view drifts between calls, so a sweep that does not settle the grid back to a known state
measures everything that came before it - which showed up as one pivot apparently dragging five
dimensions onto the left axis. And the order of the POV row is not stable across resets either, so a
source column names a different dimension from one call to the next even when the axes look identical -
which showed up as the wrong dimension moving, in a pattern with no discernible logic. `PivotOracleIT`
pins both before measuring anything.

What the action cannot do, `setLayout` can, and the last test in that class does the same rearrangement
that way for comparison: write the dimension names where they are wanted and let the server read the
sheet. That is the mechanism for rearranging a grid, and a client computing a pivot locally and sending
the result - which is what Jaygrid does, and what the connector needs - is not working around a missing
verb but using the one that exists.

The consequence for this corpus is that pivot cannot be diffed the way the other four were. There is no
engine answer to compare against, because the engine will not perform the operation.

### The layout legality harness

What can be asked instead is narrower: whether a grid Jaygrid's pivot produces is one Essbase accepts
and reads back the same way. A sheet the server reads differently from how the client meant it looks
perfectly reasonable in the labels - the dimensions simply come back somewhere nobody asked for, and the
first sign of it is a grid of wrong numbers. The connector hands exactly this sheet onward, so it is
worth knowing.

`GeneratePivotLayouts` in jaygrid pivots a set of grids and writes each result, with the placements
Jaygrid meant, to `pivot-layouts.json`. `PivotLayoutLegalityIT` in essbase-rest-client submits each one
through `setLayout` and compares what the server reports against what was meant. Regenerate the file
when Jaygrid's pivot changes; it is copied between the two projects by hand, like the fixtures.

All seven layouts checkable today pass, the seven-deep top axis among them: every grid Jaygrid's pivot
produces is legal and unambiguous. It does not say the layout Jaygrid chose is the *right* one - that is
a question about matching Smart View, not about the engine, and nothing here can settle it.

## Difference: where the POV row is laid out

Essbase begins a POV row at the column the left axis ends on - one dimension on the left and it starts at
column 1, two and it starts at column 2. Jaygrid begins it at column 1 regardless. So the two agree while
one dimension is on the left and part company at two.

Neither is wrong on its own terms, and nothing here needs Jaygrid changed. What it means is that **a
column number taken from one grid does not name the same dimension in the other**, so anything carrying
coordinates between them has to translate. `EssbaseOracleDiffTest.povColumnOf` does that by finding the
member the fixture clicked rather than replaying its column.

Worth recording how this was nearly mis-called. Replayed by column number, the two-left POV pivots looked
like an off-by-one inside Jaygrid: every click moved the dimension to the right of the one asked for, and
clicking the last one moved nothing - five fixtures, all consistent, all apparently engine-confirmed. The
evidence was real and the conclusion was wrong, because the comparison was asking Jaygrid for a different
cell than it asked Essbase for. Matched by member, all five agree. `CubeViewPovColumnTest` pins the layout
difference itself so it stays visible.

data, and this cube has none loaded, so a fixture for either would prove nothing. They need a cube with

One thing the characterization baseline surfaced that no oracle has ruled on yet: Keep Only on a
seven-deep top axis moves the outermost dimension into the POV.

One divergence noticed while capturing the zooms and not yet acted on: a selection spanning two regions
is ignored down to the region it started in by Essbase, where the ranged operations here throw
"Selected ranges must be in same grid region". Zoom already matches Essbase; keep only and remove only
do not.
